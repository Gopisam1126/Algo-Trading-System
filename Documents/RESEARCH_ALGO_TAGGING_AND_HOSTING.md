# Kite stamps the algo tag; self-hosting stands

As of 21 Nov 2026, the evidence settles both open items in the system's favour. **On B1, the client sends nothing.** NSE's operational modalities make the *trading member* write the exchange's generic algo ID onto every sub-threshold client API order: "99999" in the Algo ID field and NNF ID 444444444444 with 13th digit "0". BSE's equivalent is sixteen nines. A Zerodha staff reply of 23 Jul 2026 says a sub-10 OPS user does "not need to provide an Algo ID or pass any value in the corresponding field", so `algo_id` stays unset in `place_order`. Confidence is **high**. **On B10, the system may host itself.** NSE's standard I(h), "All Retail Algorithms ... should be hosted on brokers' cloud servers", sits in a list of broker obligations and never defines "Retail Algorithm". NSE's own FAQ of 3 Nov 2025 carves this case out (Q5: the tech-savvy client hosts "at their end where Algo logic resides"). Zerodha staff confirmed on 30 Jul 2026 that sub-10 OPS strategies may run on the user's own cloud, and every broker that has published a reading agrees. Confidence is **moderate-high**. The weak point is the text. NSE's April 2026 consolidated circular repeats the broad hosting rule without the carve-out, and the FAQ says it does not bind NSE. **No SEBI, NSE, BSE or Zerodha text requires the client's server or static IP to be in India.** The India rule applies to the broker's order-routing server. The planned India-region VPS is therefore a sound engineering choice, not a legal requirement. B1 can close on one written reply from Zerodha. B10 does not block buying the VPS. It closes on the same reply, plus one narrow question to counsel if the owner wants the remaining textual risk covered. This report is research written for the system's owner. It is not legal advice.

## B1: Zerodha applies the generic ID, and the order request carries nothing new

### Answer: leave `algo_id` unset (confidence: high)

**Zerodha, not the client, tags this system's sub-threshold Kite Connect orders.** The exchange defines the value and the broker writes it into the exchange order message. No regulator, exchange or Zerodha text asks a client below 10 OPS to send any identifier. In practice, **omit `algo_id`**. pykiteconnect strips parameters left as `None` before the POST, so leaving it out sends nothing ([pykiteconnect connect.py](https://github.com/zerodha/pykiteconnect/blob/master/kiteconnect/connect.py)). Confidence is high on what the client must do. It is only moderate on how Zerodha applies the tag internally, because Zerodha has never said in so many words that it sends "99999".

### The exchange texts put the duty on the broker

SEBI created the duty and left the mechanics to the exchanges. Its circular of 4 Feb 2025 requires algo orders to be "tagged with a unique identifier provided by the Exchange". That requirement (5.II(b)) sits under the heading for stockbrokers' roles and responsibilities. The same circular requires self-developed algos to be registered "only if they cross the specified order per second threshold" (5.I(c)) ([SEBI circular, 4 Feb 2025](https://www.sebi.gov.in/sebi_data/attachdocs/feb-2025/1738665456458.pdf)). NSE's implementation standards of 5 May 2025 then created the sub-threshold lane in B.3. Such orders "shall also be tagged as 'Algo'", they "wouldn't require registration", and "a generic algo ID shall be provided by the Exchange". Section G adds that all algo orders, "(Below and above the threshold)", carry an exchange identifier ([NSE/INVG/67858](https://nsearchives.nseindia.com/content/circulars/INVG67858.pdf)). B.3 says who *issues* the ID, not who *applies* it.

**The Detailed Operational Modalities of 22 Jul 2025 answer that.** For "non-registered algos (within 10 orders per second i.e. OPS) developed by clients", para 8.2.4 says "members shall be required to send the value in the Algo ID field as "99999" in the order message and 13th digit of the 15 digit NNF ID as "0"". Para 10.6 says the trading member "shall have suitable system in place to identify orders being sent by the client are below or above the defined threshold and appropriately tag the algo id" ([NSE/INVG/69255](https://nsearchives.nseindia.com/content/circulars/INVG69255.zip)). A corrigendum fixes the Client Direct API NNF ID at 444444444444, with an algo 13th digit of 0, 2 or 4 ([NSE/INVG/69289, 24 Jul 2025](https://nsearchives.nseindia.com/content/circulars/INVG69289.pdf)). Since 4 Aug 2025, NSE has rejected orders whose NNF ID and Algo ID fields disagree, before they reach the market ([NSE/CMTR/69295](https://nsearchives.nseindia.com/content/circulars/CMTR69295.pdf)). The April 2026 consolidated circular repeats both duties in paras 8.4.7 and 8.4.8.6 ([NSE/INVG/73992, 30 Apr 2026](https://nsearchives.nseindia.com/content/circulars/INVG73992.zip)).

BSE uses the same model with its own encoding. The Algo ID is "9999999999999999", and the 14th digit of the 16-digit location ID 4444444444444 is set to "1". The flag runs the opposite way to NSE: on BSE "1" marks an algo order, while on NSE "0" does. BSE's SOP again says "members shall be required to send" the value ([BSE revised SOP, 29 Aug 2025](https://www.bseindia.com/markets/MarketInfo/DownloadAttach.aspx?id=20250829-12&attachedId=372c4b74-a5ac-4e29-a32b-1fb294117c38); [BSE location-ID table](https://www.bseindia.com/markets/MarketInfo/DownloadAttach.aspx?id=20250829-12&attachedId=40332ec4-6508-4d2d-8901-a966dd6989e6)). All of these are fields in the exchange order message, which only the broker composes. A Kite Connect client never sets either value.

### Zerodha's words, code and docs agree

Zerodha planned this in May 2025. A developer asked whether retail algos would get "a generic algo ID" tied to the API key, and Matti replied "Yes, that is the plan for now" ([kite.trade 15015, May 2025](https://kite.trade/forum/discussion/15015/revising-kite-connect-fees-from-2000-to-500-per-month)). Zerodha's explainer of 6 May 2025 lists "Orders tagged with generic ID (unregistered, ≤10 OPS)" ([Z-Connect, 6 May 2025](https://zerodha.com/z-connect/general/a-comprehensive-overview-of-nses-circular-on-the-new-retail-algo-trading-framework)). **The most direct statement came on 23 Jul 2026.** Asked whether an own-account individual needs an exchange Algo ID, salim_chisty wrote: "If your order placement rate is below 10 orders per second (OPS), exchange algo registration is not required." He added: "In that case, you do not need to provide an Algo ID or pass any value in the corresponding field while placing orders" ([kite.trade comment 52674](https://kite.trade/forum/discussion/comment/52674/#Comment_52674)). On 12 Aug 2026 Sravanthi_bh gave a self-developed, own-account user the same answer: "No separate Algo ID or exchange approval/registration is required if you stay within the prescribed 10 OPS threshold" ([kite.trade 16176, "Sub-threshold"](https://kite.trade/forum/discussion/16176/sub-threshold)).

The REST documentation agrees by leaving the field out. The orders page lists every placement parameter up to `market_protection`, `autoslice` and `tag`, and has **no `algo_id` at all** (fetched 21 Nov 2026) ([Kite Connect orders docs](https://kite.trade/docs/connect/v3/orders/)). The SDKs gained an *optional* `algo_id` in mid-2026. It merged in gokiteconnect on 29 Jun 2026 and in pykiteconnect on 23 Jul 2026, the same day as the forum answer above. Neither PR says who should send it ([pykiteconnect PR #234](https://github.com/zerodha/pykiteconnect/pull/234); [gokiteconnect PR #128](https://github.com/zerodha/gokiteconnect/pull/128)). Zerodha's FAQ ties a "unique Algo ID" only to registration above 10 OPS ([Kite Connect API FAQs](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/kite-connect-api-faqs)). The most likely reading is that the field carries a *registered* strategy's unique ID, but no Zerodha source says so.

Every other broker that addresses the point treats tagging as the broker's job. Kotak Neo is explicit: its "APIs automatically append the appropriate Algo ID" ([Kotak Neo](https://www.kotakneo.com/platform/kotak-neo-trade-api/static-ip-details/)). 5paisa gives each client "one non-algo app, with a limit of 10 orders per second, and no Algo ID is required" ([5paisa forum, 26 Sep 2025](https://tradebetter.5paisa.com/t/important-update-sebi-algo-compliance-effective-1st-april/761)). Upstox asks for an `X-Algo-Name` header only from registered "Algo Apps" ([Upstox](https://upstox.com/developer/api-documentation/announcements/algo-trading-circular/)). Angel One says sub-threshold algos "will use a generic algo ID provided by the exchange" ([Angel One, 25 Feb 2026, updated 13 Mar 2026](https://www.angelone.in/news/market-updates/what-s-changing-in-angel-one-s-smartapi-access-from-april-1-2026)). Developer reports from the 1 Apr 2026 go-live show the same thing. The rejections Kite users posted were about IP whitelisting and market protection, and **no Zerodha forum post reports an order rejected for a missing or wrong algo ID** ([kite.trade 15912](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types)).

### Two misprints and one unanswered question keep B1 open on research alone

Three things stop the research from closing B1 by itself.

**First, Zerodha has never said in writing that it applies the tag.** The 12 Aug 2026 question asked directly whether tagging is "handled entirely on Zerodha's side". The answer skipped that part and replied only that no Algo ID is needed. Both replies come from handles assumed to be staff, because neither forum shows staff badges. Their years are also inferred, because kite.trade shows only the day and month for current-year comments; the 2026 dates rest on rising comment and thread IDs.

**Second, the client cannot see the tag.** NSE's mismatch check proves only that whatever Zerodha sends is internally consistent. An order sent with NNF ID 444444444444, 13th digit "0" and Algo ID "99999" passes. So does one marked non-algo with Algo ID 0. Accepted orders therefore do not prove the order was tagged. No Kite order-response field and no contract note showing the tag was found. A Dhan user's order response showed `"algoId": "0"` with no explanation ([MadeForTrade, 1 Apr 2026](https://madefortrade.in/t/dhanhq-update-safer-participation-of-retail-investors-in-algo-trading-static-ip-mpp-rate-limits/61689)). That suggests broker APIs do not echo the exchange tag at all. Under NSE's own texts, the liability for a wrong tag sits with the trading member (69255 para 10.6; 67858 I(f)).

**Third, two texts misstate B.3 in the direction that would hurt this system.** Machine text extraction of NSE/INVG/67858 loses a hidden text layer and reads B.3 as "...below the defined TOPS, require registration with the Exchange...". The rendered page actually reads "wouldn't require registration" ([NSE/INVG/67858](https://nsearchives.nseindia.com/content/circulars/INVG67858.pdf)). Separately, the April 2026 consolidated circular reprints B.3 at para 8.3.2.2(3) with "**would require registration**" ([NSE/INVG/73992, p.41](https://nsearchives.nseindia.com/content/circulars/INVG73992.zip)). That reprint is almost certainly a transcription error. The same circular keeps "the client will not be required to register" at 8.3.2.2(2), copies SEBI's "only if they cross" wording at 8.3.1.3, keeps the "only exception" for "Tech Savvy retail investor (within OPS threshold)" at 8.4.1, and repeats the unregistered "99999" rule at 8.4.7. BSE's B.3 also says "wouldn't". Anyone reading a scraped copy or the reprint alone would wrongly conclude that sub-threshold algos must register. Three further loose ends are smaller. Zerodha has not said what happens if a sub-threshold order *does* carry an `algo_id`; its SDK test uses the dummy value "algo-123". A Dec 2024 staff remark that sub-threshold API orders "won't get tagged as algo" predates the generic-ID design and no longer applies ([TradingQnA, 14 Dec 2024](https://tradingqna.com/t/query-on-future-of-apis-for-traders/160288?page=3)). And "99999" appears in practitioner writing only as an unverified snippet, although NSE's primary text now confirms the value.

## B10: NSE's broker-cloud rule covers vendor algos, not this VPS

### Answer: the system may self-host, and its server need not be in India (confidence: moderate-high on hosting, high on location)

I(h) does not, on its best reading, apply to a tech-savvy client's own sub-threshold algo. The only exchange text that speaks to this case says the client hosts at its own end. Zerodha and every other broker that has published a reading treat self-hosting behind a whitelisted static IP as compliant. On location, the texts are silent about the client and explicit about the broker. The confidence on hosting stops short of high for three reasons. The carve-out lives in a non-binding FAQ. The later consolidated circular did not repeat it. And BSE's FAQ could not be read.

### The only exchange text on DIY hosting says "at their end"

I(h) reads: "All Retail Algorithms, including those provided by empanelled Algo providers should be hosted on brokers' cloud servers" ([NSE/INVG/67858, Annexure p.6](https://nsearchives.nseindia.com/content/circulars/INVG67858.pdf)). It is item (h) of Section I, "Operational Specifications for providing algo through IBT / STWT / Client API and Vendor API". Every item in that section is a broker obligation: audit trail, OAuth, no open APIs, and full broker liability. **The circular never defines "Retail Algorithm".** The phrase "including those provided by empanelled Algo providers" points to algos that brokers or vendors *offer* to retail clients. The same document assumes client-side hosting elsewhere. A.5 says "In case of client generated algos, the static IP shall be that of the client", which only makes sense if the client's code runs on the client's machine. SEBI's circular contains none of the words "host", "server", "cloud" or "located" ([SEBI circular](https://www.sebi.gov.in/sebi_data/attachdocs/feb-2025/1738665456458.pdf)).

The July 2025 modalities stated the rule more broadly. Para 14 says "all the strategies shall be run on the brokers servers. The order messages shall be originated from brokers server" ([NSE/INVG/69255](https://nsearchives.nseindia.com/content/circulars/INVG69255.zip)). **NSE's FAQ of 3 Nov 2025 then narrowed it.** Q4 reads para 14 as meaning "all Algos developed by Algo Providers need to be hosted on the Trading Member's server". Q5 quotes para 14 and adds: "**However, Tech Savvy client is required to host the Algo using a static IP at their end where Algo logic resides instead of hosting the Algo on Trading Member's cloud server.**" Q3 and Q6 say a client static IP is needed "only in case of Tech savvy Investor using API". Q10 gives a vendor platform hosted on broker infrastructure the broker's IP ([NSE FAQ, 3 Nov 2025](https://nsearchives.nseindia.com/web/sites/default/files/inline-files/FAQ_Retail_Algo_03112025_NSE.pdf)). The structure is consistent. A tech-savvy client needs its own static IP precisely because its algo runs outside the broker. If it ran on the broker's cloud, it would sit behind the broker's IP, as a vendor's does. Even the literal para 14 sentence about order messages is met by any Kite Connect order. The client sends an HTTPS request, and Zerodha's own system builds the exchange order message and routes it "through the members' trading system" (69255 para 10.2). That last point is this report's inference, not NSE's statement.

Zerodha's position moved from caution to permission. Its 6 May 2025 explainer listed "hosted on broker's cloud servers" for all three algo types, and Team Zerodha replied in the comments that "That bit will be revised out of the circular" ([Z-Connect, 6 May 2025](https://zerodha.com/z-connect/general/a-comprehensive-overview-of-nses-circular-on-the-new-retail-algo-trading-framework)). In July 2025 Matti wrote that "The SOP requires that all algo strategies be hosted on the broker's cloud" and said brokers had asked the exchanges and SEBI to reconsider. Users' follow-up questions there in Jul and Sep 2025 went unanswered ([kite.trade 15350](https://kite.trade/forum/discussion/15350/notes-on-the-nse-circular-prescribing-operating-procedures-for-api-usage)). **On 30 Jul 2026, nagavenij answered a user running exactly this profile**: an own-account system on "my own cloud server located in India (Mumbai region), not on Zerodha's infrastructure". The reply said strategies at "10 orders per second (OPS) or fewer" may run on "preferred infrastructure, including cloud providers such as AWS, GCP, Azure", provided "the applicable API requirements (such as using the registered static IP for order placement) are met" ([kite.trade comment 52689](https://kite.trade/forum/discussion/comment/52689/#Comment_52689); [thread 16136](https://kite.trade/forum/discussion/16136/broker-cloud-hosting-requirement-does-it-apply-to-me)). Zerodha's static-IP support article lists "internet service providers (ISPs), cloud, or Virtual Private Server (VPS) providers" as IP sources ([Zerodha support](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/static-ip)). Its 31 Mar 2026 explainer describes running from a cloud IP ([In The Money by Zerodha](https://inthemoneybyzerodha.substack.com/p/sebi-algo-trading-changes-april-2026)). On 13 Apr 2026 staff told a user who travels to use a "fixed cloud-based/VPS setup" ([kite.trade 15976](https://kite.trade/forum/discussion/15976/static-ip-address)). No Zerodha hosting product for Kite Connect users has been reported either; users who asked in Mar 2026 got none ([TradingQnA 189901](https://tradingqna.com/t/static-ip-for-algo-trading-in-zerodha/189901)). If I(h) bound personal apps, Zerodha would be offering no compliant way to use Kite Connect at all.

Other brokers draw the same line between their own clients' code and vendors' platforms. **Angel One restates the broad NSE rule and the carve-out side by side.** Retail algos are to be "hosted on the Trading Member's (broker's) server", while tech-savvy clients "maintain their own logic and host using a registered Static IP at their end" ([Angel One, 25 Feb 2026, updated 13 Mar 2026](https://www.angelone.in/news/market-updates/what-s-changing-in-angel-one-s-smartapi-access-from-april-1-2026)). Fyers requires "External platforms" to be "empanelled and hosted within the broker's infrastructure", while telling DIY users to use an ISP static IP or a cloud server ([Fyers notice, 10 Mar 2026](https://fyers.in/notice-board/new-sebi-framework-for-retail-algo-trading-from-april-01-2026); [Fyers Community](https://fyers.in/community/t/sebis-new-algo-trading-rules-kick-in-on-april-1-here-is-what-changes-for-you/12267)). Kotak puts fintech partners on broker systems and tells DIY users to "Run your trading algorithm from the system where the static IP is configured", naming AWS, DigitalOcean, Azure and GCP ([Kotak Neo](https://www.kotakneo.com/platform/kotak-neo-trade-api/static-ip-details/)). Groww writes that "You can host your trading system on a cloud server with a static public IP" ([Groww, 2 Sep 2026](https://groww.in/blog/static-ip-api-trading-setup)). Dhan offers a broker-hosted runtime, Dhan Cloud, as an option. It is exempt from the static-IP rule that applies to "external API order placement environments", which confirms those external environments still exist ([Dhan support](https://dhan.co/support/platforms/dhanhq-api/is-a-static-ip-required-for-dhan-cloud/)). After go-live, DIY Kite users ran on AWS, PythonAnywhere, laptops and VPSs. Their failures were whitelist mismatches, and **none reported being told to move to a broker cloud** ([kite.trade 15933, 1 Apr 2026](https://kite.trade/forum/discussion/15933/static-ip-clarification); [TradingQnA 197313, 22 Aug 2026](https://tradingqna.com/t/why-kite-connect-api-orders-started-failing-after-static-ip-enforcement/197313)). Two secondary sources disagree. A Kotak explainer says retail algos must sit on "Exchange-approved servers" ([Kotak Neo explainer](https://www.kotakneo.com/investing-guide/articles/retail-algo-trading-rules-nse-circular/)), and a vendor says "Indian servers" ([AlgoBulls](https://algobulls.com/blog/industry-insights-and-updates/sebi-new-algotrading-regulations-for-retail-investors-2026)). Neither cites a primary text, and both conflict with their own broker's or the exchange's position.

### The April 2026 consolidation is where the remaining risk sits

The strongest argument against self-hosting comes from NSE's current master text. The consolidated circular of 30 Apr 2026 restates I(h) as para 8.4.8.16, now "hosted on brokers' cloud servers/environment", and repeats para 14 word for word as para 8.9. **A search of its 74 pages finds no reproduction of FAQ Q5's carve-out** ([NSE/INVG/73992](https://nsearchives.nseindia.com/content/circulars/INVG73992.zip)). The FAQ is not in the circular's list of compiled documents. The FAQ's own disclaimer says that in any inconsistency "the Information in the circulars shall be construed as final and binding" and that "Nothing stated herein shall bind NSE" ([NSE FAQ](https://nsearchives.nseindia.com/web/sites/default/files/inline-files/FAQ_Retail_Algo_03112025_NSE.pdf)). Read strictly, the binding text is broad and the narrowing text is not binding.

The counter-reading is stronger, for three reasons. First, the consolidation *did* absorb two FAQ answers that only make sense if the client hosts the algo itself. A note after para 8.4.8.28 records that static IP "is restricted only to 'Tech -savvy' Retails investors", and para 3.2 exempts tech-savvy clients from mock trading. Second, the circular says no information was rescinded in the consolidation. Third, the same document contains the "would require registration" misprint discussed under B1. That misprint shows the consolidation was not proofread closely enough to read deliberate policy into what it left out, in either direction.

The BSE side is less certain. BSE's standards and SOP carry the same broad wording. **BSE's FAQ, reported as dated 3 Nov 2025, could not be retrieved.** The only trace is a search-result summary of a third-party mirror whose page returned 404. That summary says static IP is needed only for tech-savvy API users *and* that strategies must be hosted on the broker's servers. It cannot be checked, and it is ambiguous on exactly this point ([mirror, unverified](https://rhnvrm.github.io/stock-market-circulars/circulars/bse/2025/bse-2025-11-03-40abb749f2221253-faqs-on-safer-participation-of-retail-investors-in-algorithmic-trading)). No BSE consolidated circular like NSE's was found. BSE's SOP para 8.2.1 also leaves out NSE's phrase "with the only exception of 'Tech Savvy retail investor (within OPS threshold)'", although its 8.2.4 assumes that exception ([BSE revised SOP](https://www.bseindia.com/markets/MarketInfo/DownloadAttach.aspx?id=20250829-12&attachedId=372c4b74-a5ac-4e29-a32b-1fb294117c38)).

The Zerodha evidence has its own limits. nagavenij is assumed to be staff, with no badge shown. The year of the reply is inferred. The fetch tool limited verbatim quotes, so the reply is known partly in paraphrase. No primary Zerodha page withdraws the 2025 "hosted on broker's cloud servers" line. Finally, no NSE circular after 30 Apr 2026 that changes these rules was found, but NSE's circular index for May to Nov 2026 was not checked entry by entry. "No change since April" therefore remains unconfirmed.

### No text puts the client's server or IP in India

**Every India-location requirement in the texts concerns the broker.** NSE's modalities say "The broker's server routing API /Algo Provider orders to the exchange trading system shall be located in India" (69255 para 10.2). The consolidated circular says "The Algorithmic orders are routed through broker servers located in India" (73992 para 8.1.1). BSE's SOP para 10.2 matches ([NSE/INVG/69255](https://nsearchives.nseindia.com/content/circulars/INVG69255.zip); [NSE/INVG/73992](https://nsearchives.nseindia.com/content/circulars/INVG73992.zip)). Zerodha's own servers satisfy that requirement. The SEBI circular, NSE 67858, 69255, 69289, 70309 and 73992, the NSE FAQ, and BSE's standards and SOP were each searched for "India", "located", "host", "server" and "cloud". None places a requirement on the client's machine or IP. The single positive Zerodha statement is informal and predates go-live: Team Zerodha replied on 19 May 2025 that there is "No mandate for the IP to be from India" ([Z-Connect comments](https://zerodha.com/z-connect/general/a-comprehensive-overview-of-nses-circular-on-the-new-retail-algo-trading-framework)). Zerodha's support pages, Kotak's list of global cloud providers, and every other broker page reviewed are equally silent. The one post-go-live rejection involving a probably non-Indian IP said the address was "not allowed to place orders for this app", which is a whitelist failure, not a location check. The researcher's note that the IP belongs to an AWS US range was not verified ([kite.trade 15933](https://kite.trade/forum/discussion/15933/static-ip-clarification)). SEBI's cloud, CSCRF and outsourcing frameworks were not examined in depth. They bind regulated entities, not individual clients, and no provision applying them to a client's algo server was found.

The answer therefore holds with high confidence on the texts and moderate confidence on practice. The question does not affect this system, because an India-region VPS meets every reading. India still earns its place for latency: Team Zerodha recommended AWS Mumbai to a reader in May 2025. It also matters for the project's own data-reachability probe (B8). The project's audit HAL-001 rightly records India hosting as **this system's own rule**, not a regulatory one.

## Kite enforces the IP, the rate and market protection, not the tag

The rules that actually reject orders are operational ones, and they apply whatever the order rate. **Since 1 Apr 2026, every order request must come from a whitelisted public static IP.** "All order requests from an unregistered IP will be rejected", regardless of order frequency ([Matti, kite.trade 15912, 25 Mar 2026](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types)). The account may register **at most two IPs**: a primary, which is mandatory, and an optional secondary. They are set on the developer profile and apply "at the account level and not at the individual app level" ([salim_chisty, 7 Jul 2026](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types/p2); [Zerodha support](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/static-ip)). The project's pre-live checklist line "One IP per app" (row B6) is therefore wrong and should say two IPs per developer profile, shared across apps. Changes are limited to **one per calendar week**. That follows NSE A.6, which lets a client write to the broker "in extraordinary cases". Updates take effect "almost instantly" ([NSE/INVG/67858](https://nsearchives.nseindia.com/content/circulars/INVG67858.pdf); [Nivas, 24 Jun 2026](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types/p2)). Whether changing the primary and the secondary counts once or twice against that limit has been asked and not answered. Only public static IPs are accepted: "private/local, or dynamic IPs may result in order rejections" (salim_chisty, 7 Jul 2026). Each IP is checked for uniqueness. It may be shared only with a spouse, dependent children and dependent parents, through separate apps under one developer profile and a declaration. Sharing outside the family risks suspension ([Kite Connect API FAQs](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/kite-connect-api-faqs)). **IPv4 and IPv6 are both accepted, and the address family is a trap.** One user registered IPv6 while his requests left over IPv4 and were rejected. Staff said the address family "is not controlled at the KiteConnect library/SDK level" ([Arockiya_r, 31 Mar 2026](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types)). The fix is to pin the VPS's egress to one family or register both addresses, using the two slots. That second option leaves no failover IP.

The IP check covers **order placement, modification and cancellation only**. Matti put it as "The static IP will only be for the order place/modify/cancel endpoints" in May 2025 ([kite.trade 15015](https://kite.trade/forum/discussion/15015/revising-kite-connect-fees-from-2000-to-500-per-month)). On 23 Sep 2026 Nivas added that "The GTT endpoints do not require requests to originate from the same static IP" ([kite.trade 15912 p2](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types/p2)). The WebSocket, order book and positions APIs work from any IP ([Zerodha support](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/static-ip)). One user reported a cancel accepted from a non-whitelisted address in Aug 2026, and the case was never resolved. The system should not rely on that ([kite.trade 16193](https://kite.trade/forum/discussion/16193/static-ip-for-order-cancellation-via-api)).

**The rate limit is 10 orders per second per Kite client ID, across all apps**, and orders above it are rejected rather than queued. In staff's words, "10 orders will be placed, and 5 orders will be blocked with a 429 response". The limit is "kite client ID specific" ([Arockiya_r, 28–31 Mar 2026](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types)). The documentation adds **400 orders per minute**, a cap of **5,000 orders per day** per user or API key "across all segments and varieties", and **25 modifications per order** ([Kite Connect exceptions docs](https://kite.trade/docs/connect/v3/exceptions/)). Extra API keys do "not bypass or multiply the account-level order-placement limit" ([salim_chisty, 27 Aug 2026](https://kite.trade/forum/discussion/16217/are-there-any-hidden-rate-limits)). **Rejected and invalid requests count toward the limit** ([Kite Connect API FAQs](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/kite-connect-api-faqs)), so retry loops are the real burst risk. Two details matter for this system. NSE sets its threshold "per exchange /segment" and measures it on "the calendar clock second of the broker server" (67858 B.2 and F). Zerodha's limit is stricter: NSE and BSE orders share **one** 10-per-second budget per client ID. The checklist reading of "10 OPS per exchange and segment" is the exchange's threshold, and `MAX_ORDERS_PER_SECOND` must be a single cap across both exchanges. Zerodha has not said whether modify and cancel calls count toward the 10 per second, or whether it counts calendar seconds or a rolling window. NSE also requires unregistered algos to run through a single predefined API key (A.4), and staff say apps are "intended to be associated with a single client ID" (Nivas, 13 Nov 2026). In practice that means one personal app for one client ID.

**MARKET and SL-M orders must carry a non-zero `market_protection`.** The allowed values run from greater than 0 up to 100, or -1 for automatic. "Orders placed with market protection set to "0" will be rejected" ([Matti, 25 Mar 2026](https://kite.trade/forum/discussion/15912/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types); [Kite orders docs](https://kite.trade/docs/connect/v3/orders/)). The exchange rule behind this is "Algo orders with order type as Market Order are not permitted" (NSE FAQ Q11, quoting NSE/MSD/67753 point 8.1.1.12). Market protection turns a market order into a limit order, and orders outside the exchange's LPP (limit price protection) band can still be rejected. LIMIT and SL orders are unchanged ([Matti, TradingQnA, 30 Mar 2026](https://tradingqna.com/t/preparing-to-comply-with-sebis-retail-algo-rules-static-ip-ratelimits-order-types/192636)). Autoslice is capped at 10 slices. Sessions must be logged out before the next trading day (NSE A.8), and login requires TOTP or 2FA.

## A support ticket and one counsel question close both items

### B1 closes on Zerodha's written confirmation

The research already supports the engineering decision: **send no `algo_id`**. The project's adapter already sends one only when it is configured, so B1 needs a record, not code. A Zerodha support reply in writing, carrying a ticket number and tied to the owner's client ID, confirming two points would close it. The points are that Zerodha applies the generic algo ID on NSE and BSE, and that the client should leave `algo_id` unset. The ticket number, its date and the quoted sentence go into `broker.algo_tagging_confirmation`. Until the reply arrives, salim_chisty's comment 52674 is the best written, dated and public statement to record as interim evidence. Because the client cannot observe the exchange tag, the pre-live step "confirmed on a real order that what the answer requires is what the order carries" should become two checks: the outgoing request carries no `algo_id`, and the order is accepted. Zerodha might name a place where the tag is visible (question 2 below), and that would allow a third check. B1 should reopen only if one of three things happens. Zerodha documents `algo_id` as required. An NSE or BSE circular moves the tagging duty to the client. Or developers start reporting algo-ID rejections.

### B10 does not block the VPS; Zerodha's reply closes it, counsel covers what is left

The procurement in B6 can go ahead now. An India-region VPS with a dedicated static IP fits the NSE FAQ, Zerodha's 30 Jul 2026 reply and every broker's practice. The only reading it fails is a literal broker-cloud reading that Zerodha neither enforces on personal apps nor offers an alternative for. If the answer ever went the other way, the fallback would be a broker-hosted runtime such as Dhan Cloud, not a different VPS. B10 closes when Zerodha confirms in writing that this profile may self-host for both NSE and BSE orders. Several further pieces of evidence would make the closure firmer: the text of BSE's FAQ; an NSE circular or revised FAQ after April 2026 that restates Q5; or a primary Zerodha support page saying the same as the forum reply. Counsel's answer to the narrow question below covers the risk that remains on the text. That risk is not whether Zerodha permits self-hosting. It is whether the client could be exposed if an exchange ever enforced the broad reading of 73992 para 8.4.8.16 against brokers.

### The narrower question for counsel

Counsel does not need to address tagging. On the face of NSE/INVG/69255 para 10.6 and the broker-liability clause I(f), tagging is the broker's duty and the broker's liability. The one question worth paying for is this:

> Under SEBI circular SEBI/HO/MIRSD/MIRSD-PoD/P/CIR/2025/0000013 (4 Feb 2025) and the NSE and BSE texts implementing it, consider the following. NSE/INVG/73992 (30 Apr 2026) para 8.4.8.16 says retail algorithms "should be hosted on brokers' cloud servers/environment", and para 8.9 says "all the strategies shall be run on the brokers servers". NSE's FAQ of 3 Nov 2025, Q5, says a tech-savvy client "is required to host the Algo using a static IP at their end where Algo logic resides". That FAQ states that circulars prevail and that it does not bind NSE, and the consolidated circular does not reproduce Q5. Does an individual breach any obligation that binds him as a client, as distinct from the broker, by running a self-developed algorithm for his own account only, below 10 orders per second, on a VPS he rents, with a static IP that his broker has whitelisted and with his broker's written permission? If an exchange enforced the broad reading of para 8.4.8.16, what would the client's exposure be beyond the broker withdrawing API access?

## Conclusion

The research changes where the system's compliance risk lies. Both B1 and B10 were framed as gaps in what the client must *do*. On the evidence, the client must do nothing for tagging, and nothing beyond what is already planned for hosting. The tagging duty and the India-location rule both bind Zerodha, and Zerodha's liability for them is written into NSE's texts. What remains is a records problem: getting answers that can be attributed to Zerodha and filed. It is not an engineering problem. The rules that can actually stop orders are elsewhere. A wrong egress IP, or an IPv4/IPv6 family mismatch, can lock order placement for up to a week. A missing `market_protection` on the square-off path rejects the exit. And invalid retries spend a 10-per-second budget that NSE and BSE orders share at Zerodha, even though NSE counts its threshold per exchange. These deserve the pre-live testing effort that the tagging question has been absorbing.

The regulatory texts themselves are the second lesson. NSE's current master circular contains a misprint that reverses the sub-threshold registration exemption, and a hidden text layer makes machine extraction of the 2025 standard read the same way. It also restates a hosting rule that NSE's own FAQ narrows. Any automated or AI-assisted re-read of these documents can therefore produce a false alarm. The December review that already re-checks the 10 OPS threshold should also check for a revised NSE FAQ, a new NSE consolidated circular or a BSE equivalent, and any Zerodha documentation of `algo_id`. It should compare each against the rendered pages, not against scraped text.
